### LAN: an unreachable unit no longer stops Signal K

- Fixed: when a unit could not be reached on the LAN (no power, off the Wi-Fi, rebooting, a refused connection, a wrong protocol answer), the Tuya library reported the error in a way nothing caught, and the whole Signal K server process exited. With a fixed IP in the config, systemd restarted Signal K straight into the same failure for as long as the unit was away. The plugin now handles these errors at every step (connect, read, after a disconnect): the unit shows as disconnected and the plugin tries again every 15 s, as it was meant to.
- Fixed: stopping the plugin (an Admin save, a Signal K restart, disabling it) while a reconnect was in progress left that new LAN connection open. Tuya units usually accept one LAN client, so the restarted plugin could then not connect. That connection is now closed as soon as the attempt ends. A connection that timed out before the Tuya handshake finished is now closed too; before, its socket could stay open.
- Fixed: each start that failed to connect and was stopped before it finished (for example an Admin save while the unit was away) left a poll timer behind.
- Tested on a live D13 kept off the boat Wi-Fi for 4 minutes: Signal K kept running, the card showed the unit as not answering, and the plugin reconnected on its own about 20 s after the unit was back, with External still on.

### LAN: connection lines in the Signal K log

- The Signal K log now gets one line when a unit's LAN connection is lost, with the error (for example `connect EHOSTUNREACH` or `connection timed out`), and one line when it is back, with how long it was away, for example `signalk-alecoair: d13: LAN connection back after 3 min 40 s offline`. A unit that cannot be reached when the plugin starts gets *LAN connection failed at start* instead, and a short drop that is back on the first reconnect gets a single *dropped … and was back after* line. The lines are written without debug logging (`journalctl -u signalk`), never once per retry, and never with the device id or the local key.

### Store: local keys survive a damaged file

- The plugin's store (local keys, learned protocol and datapoints, External state) is written crash-safe: a temp file in the same folder, flushed to disk, renamed over the store, then the folder is flushed too. The previous good copy is kept as `signalk-alecoair.store.json.bak`.
- If the store cannot be used at start, for example empty after a power cut or not valid JSON, the plugin no longer starts silently with no keys. It writes an error to the Signal K log, keeps the damaged file as `signalk-alecoair.store.json.corrupt-` plus a timestamp, and uses the `.bak` (and writes it back as the store). The Admin status of the plugin then starts with *Store … is damaged … Using the last good copy*. With no usable `.bak` the plugin shows an error in Admin until a new AlecoAir sign-in brings the keys back; the damaged file stays for recovery by hand.
- A store file that exists but cannot be read (permissions, disk error) is never overwritten. A store that has local keys is never replaced by one without any, except by **Forget account** in Admin.

### Tests

- The Signal K plugin registry marked the tests of 0.0.4 and 0.0.5 as failing: the three WebApp layout tests start a real Chrome, which hangs in the registry's sandbox until its 240 s limit. They are now skipped when `SIGNALK_REGISTRY_TEST` is set, and every call to Chrome gives up after 15 s.
- New tests for the LAN errors (refused, unreachable, timed out, an unparsable packet, an error after disconnect, a half-open connection), for stop during a reconnect and during a failed start, for the connection log lines, and for the store recovery.
